# Spec: 让学习通待办成为日常可用的工具

**Date**: 2026-07-26
**Status**: ready-for-agent
**Scope**: Windows + Android，个人使用

---

## Problem Statement

工具现在能构建、能过测试、能同步出正确的待办列表，但**不是一个可以每天依赖的工具**。用户的实际体验是：

1. **它不告诉你它坏了。** Cookie 过期后，托盘继续显示上次成功同步的时间，定时器继续每 60 分钟徒劳地请求学习通，界面上没有任何异常。用户以为「没有新作业」，实际是「工具已经不工作了」。同一类失败还包括：自启路径失效、解析器因页面改版而失灵。

2. **提醒只响一次，而且太早。** 目前只有一条规则：截止前 72 小时触发一次，此后永远沉默。用户在截止前 3 天收到一次提醒，然后在真正该动手的时候什么都收不到。

3. **Android 端基本是残废的。** 没有登录入口（只能手动粘贴 Cookie）、没有任何通知能力、没有后台执行。手机上的这个 App 只是一个需要手动打开才能看的只读列表。

4. **打开就要等。** 一次完整同步 18.6 秒。Windows 上有常驻进程吸收掉，用户看不见；Android 上是「点开图标—盯着转圈—等 18 秒」。而 Android 的提醒依赖用户主动打开 App 来刷新数据 —— 如果打开这件事本身很痛苦，用户就不会打开，预排的提醒就永远钉在陈旧数据上。

5. **装不上，也不知道有新版。** 只有一个未签名的 ZIP，没有固定安装路径，没有开机自启，没有更新渠道。每次升级都要手动下载、解压、覆盖、重新找 exe。

**贯穿这五点的是同一个东西：静默失效 —— 工具看起来在工作，实际已经不管你了。**

---

## Solution

把工具补成两端各自独立、都能自己站住的形态：

- **Windows**：装好之后开机自启、常驻托盘、后台定时同步、到点弹通知。失效时必须**主动告诉你**，而不是安静地假装正常。
- **Android**：能在 App 内登录、能预排本地闹钟。即使几天不打开 App，该响的提醒照响。
- **两端 standalone**：各自抓取、各自存储、各自提醒。同一项作业会在两台设备上各提醒一次 —— 这是刻意接受的代价，换来的是任何一端单独失效都不影响另一端。
- **同步快到不用等**：打开即看缓存，同步在后台跑并原地更新；同时把链路里的无用请求砍掉，从 18.6 秒压到 12 秒上下。

所有设计选择遵循同一条原则：**宁可犯可见的错，不可犯静默的漏。** 多响一次铃你会发现并抱怨；漏响一次铃你永远不会知道。

## User Stories

### 同步性能与首屏

1. As a 用户, I want 打开 App 立刻看到上次同步的结果, so that 我不用盯着转圈等 18 秒。
2. As a 用户, I want 同步在后台进行并原地更新列表, so that 我可以一边看旧数据一边等新数据。
3. As a 用户, I want 通知列表抓完就先显示条目、任务详情逐条补进来, so that 我能尽早看到部分结果而不是等全部完成。
4. As a 用户, I want 同步过程中能看到当前阶段和进度, so that 我知道它在动而不是卡死了。
5. As a 用户, I want 同步失败时保留已缓存的待办, so that 我不会因为一次网络波动就丢失整个列表。
6. As a 维护者, I want 同一轮同步不重复抓取同一个页面, so that 不浪费往返也不给学习通增加无谓负载。
7. As a 维护者, I want 已经解析过的通知详情永久复用, so that 每轮同步的请求数随时间下降而不是恒定。
8. As a 维护者, I want 通知分页在命中已知通知 ID 时提前终止, so that 稳态下只抓第一页而不是固定翻满 3 页。
9. As a 维护者, I want 优化方向只做「减少请求数」而不是「提高并发」, so that 不重蹈并发从 6 提到 8 导致总耗时恶化到 113.9 秒的覆辙。

### 受监控课程

10. As a 用户, I want 自己选择要扫描哪些课程, so that 工具不去抓我早就结课的二十门旧课。
11. As a 用户, I want 新发现的课程默认被纳入监控, so that 换学期后新课的作业不会被静默漏掉。
12. As a 用户, I want 在设置里取消勾选不想监控的课程, so that 我能把不关心的课排除出去。
13. As a 用户, I want 每天第一次同步时自动检查有没有新课程, so that 我不需要记得手动去刷新课程列表。
14. As a 用户, I want 一个「立即刷新课程列表」的手动入口, so that 我刚选完课就能马上让工具看到。
15. As a 用户, I want 在已选定课程的情况下同步时跳过课程发现请求, so that 绝大多数同步能省掉那三个串行往返。
16. As a 用户, I want 看到当前监控了几门课, so that 我能一眼确认工具盯的是不是我这学期在上的课。

### 提醒规则

17. As a 用户, I want 在截止前 24 小时收到一次提醒, so that 我有充足时间安排。
18. As a 用户, I want 在截止前 2 小时再收到一次提醒, so that 我在真正该动手的时候被叫住。
19. As a 用户, I want 24 小时那档是静默的, so that 它不会在我开会或睡觉时吵到我。
20. As a 用户, I want 2 小时那档会响铃和震动, so that 它能把我从别的事情里拽出来。
21. As a 用户, I want 同一项作业的同一档提醒只响一次, so that 我不会被重复轰炸。
22. As a 用户, I want 老师改了截止时间后重新收到提醒, so that 我不会按旧时间安排。
23. As a 用户, I want 新出现的作业不立刻弹提醒, so that 一次同步抓到十项新作业时不会瞬间刷屏。
24. As a 用户, I want 没有截止时间的事项不参与提醒, so that 不会收到无意义的通知。
25. As a 用户, I want 已经过期的事项不再提醒, so that 不会被已经来不及的事情打扰。
26. As a 用户, I want 能全局暂停/恢复通知, so that 我在考试周之外可以清净一点。
27. As a 用户, I want 通知正文默认不显示课程名和作业名, so that 锁屏时旁人看不到我的课业信息。
28. As a 用户, I want 能显式打开通知详情展示, so that 我可以在自己的设备上看到完整信息。

### Android 提醒

29. As an Android 用户, I want 提醒以本地闹钟形式预先排好, so that 即使我几天不打开 App 也照样响。
30. As an Android 用户, I want 所有已知的、未过期的待办都被排上闹钟, so that 我出差一周回来也不会漏掉期间的截止。
31. As an Android 用户, I want 闹钟能穿透系统的 Doze 打盹, so that 手机放着不动时提醒不会被推迟到截止之后。
32. As an Android 用户, I want 每次同步后按 ID 全量重排闹钟, so that 陈旧的闹钟被干净地取消而不是残留。
33. As an Android 用户, I want 重启手机后闹钟依然有效, so that 我不需要在每次重启后打开一次 App。
34. As an Android 用户, I want 点击提醒能直接跳到对应作业的详情, so that 我不用自己在列表里翻。
35. As an Android 用户, I want App 首次登录成功后才请求通知权限, so that 我在还不知道这 App 有什么用的时候不会被权限弹窗打扰。

### Android 登录

36. As an Android 用户, I want 在 App 内直接登录学习通, so that 我不需要在浏览器里翻 DevTools 手工复制 Cookie。
37. As an Android 用户, I want 登录成功后自动导入登录态并开始同步, so that 登录完就能直接用。
38. As an Android 用户, I want 保留手动导入 Cookie 的入口, so that 内置登录失灵时我还有退路。
39. As an Android 用户, I want 登录页只允许导航到学习通域名, so that 我的凭据不会被送到第三方。

### 失效可见性

40. As a 用户, I want Cookie 失效时立刻收到系统通知, so that 我不会以为「没有新作业」而其实是工具停了。
41. As a 用户, I want 失效通知在同一次失效期间只响一次, so that 我不会被同一个问题反复轰炸。
42. As a 用户, I want 重新登录成功后失效状态被重置, so that 下次再失效时还能收到通知。
43. As a Windows 用户, I want 托盘图标和状态文字反映认证失效, so that 我扫一眼就知道要重新登录。
44. As an Android 用户, I want 打开 App 时看到醒目的失效横幅和一键登录按钮, so that 我能立刻修好它。
45. As a 用户, I want 认证失效后自动同步完全停止, so that 工具不再徒劳地拿失效 Cookie 反复请求学习通。
46. As a 用户, I want 部分数据源失败时看到失败数量和诊断入口, so that 我知道这次结果不完整。
47. As a 用户, I want 诊断导出脱敏 Cookie、token 和账号参数, so that 我能安全地把它贴给别人看。

### Windows 桌面形态

48. As a Windows 用户, I want 开机自动启动并直接隐藏到托盘, so that 我不需要每天手动打开它。
49. As a Windows 用户, I want 自启默认是关闭的, so that 装完之后不会未经我同意就常驻。
50. As a Windows 用户, I want 在设置里开关自启, so that 我能自己决定。
51. As a Windows 用户, I want 关闭主窗口时隐藏到托盘而不是退出, so that 后台同步和提醒继续。
52. As a Windows 用户, I want 从托盘明确退出后进程真的结束, so that 它不会偷偷继续跑。
53. As a Windows 用户, I want 重复启动不会创建第二个实例, so that 不会出现两套托盘和两个定时器。

### 安装与更新

54. As a Windows 用户, I want 一个 setup.exe 双击就装好, so that 我不用解压 ZIP 再自己找 exe。
55. As a Windows 用户, I want 安装不需要管理员权限, so that 我在受限账户上也能装。
56. As a Windows 用户, I want 装完有开始菜单快捷方式, so that 我能正常地找到和启动它。
57. As a Windows 用户, I want 能从控制面板正常卸载, so that 不留垃圾。
58. As a Windows 用户, I want 仍然提供 ZIP 版本, so that 我想要免安装便携版时也有。
59. As a Windows 用户, I want 安装程序检测并引导安装 WebView2 运行时, so that 内置登录不会因为缺运行时而失灵。
60. As a 用户, I want App 检查是否有新版本并提示我, so that 我不会一直用着有 bug 的旧版。
61. As a 用户, I want 更新只提示不自动安装, so that 它不会在我用着的时候自己重启。

## Implementation Decisions

### 同步链路

- **`LocalSyncRunner.run()` 接口变更**：增加「上一轮同步结果」参数。这是做通知详情复用和分页提前终止的前提 —— 目前 `run()` 只接受配置，无法知道哪些通知已经解析过。返回值结构不变。

- **首页去重**：收件箱阶段和课程发现阶段目前在同一轮同步中各自抓取一次学习通首页。改为一轮同步内复用同一份首页响应。

- **通知详情复用**：通知一旦发出，内容不再变化。已解析过的通知 ID 及其提取出的任务入口链接持久化保存，后续同步直接复用，不再请求详情页。

- **分页提前终止**：通知列表按时间倒序返回。当某一页中出现已知通知 ID 时，停止继续翻页。保留现有的页数上限作为兜底。

- **任务详情不做缓存**：任务页承载 `dueAt` 和提交状态，两者都可能变化，且不请求就无法知道是否变化。分级缓存（按截止紧迫度设置不同 TTL）的方案**本轮明确不实现**，留到上述优化实测之后再判断是否必要。理由：它是唯一会引入数据陈旧的优化，而在免费的优化尚未做完之前不应该先付这个代价。

- **不调整并发度**：现有并发（通知详情 6、任务详情 6、课程列表 3×2 路）保持不变。历史实测记录显示任务详情并发从 6 提到 8 会使总耗时从 18.6 秒恶化到 113.9 秒并产生 3 个失败，说明服务端对总在途请求数敏感。所有优化只走「减少请求总数」方向。

### 受监控课程

- **新增领域概念「受监控课程」**：用户显式选定要扫描的课程空间，区别于「学习通账号下的全部课程」。持久化保存每门课的课程标识三元组（课程 ID、班级 ID、个人 ID）与标题。

- **默认纳入（opt-out）**：课程发现返回的新课程自动进入监控集合。用户可在设置中取消勾选。选择 opt-out 而非 opt-in，是因为 opt-in 的失败模式（换学期后新课一门都没勾，工具安静地盯着已结课的课）是静默的，而 opt-out 的失败模式（多抓几门课、多花一两秒）是可见的。

- **课程发现降频**：有已保存的受监控课程时，同步直接用保存的课程标识拼接任务列表 URL，跳过「首页 → 交互页 → 课程列表接口」这三个串行请求。发现流程改为每天首次同步时执行一次，另提供手动「刷新课程列表」入口。降频而非彻底跳过，是为了保证 opt-out 的保护成立 —— 不跑发现就永远不知道有新课。

- **课程列表解析扩展**：当前解析只提取课程标识和标题，其余信息丢弃。受监控课程需要在设置界面展示，解析结果需保留足以让用户辨认课程的信息。不引入基于学期或结课状态的自动过滤启发式 —— 用户的显式选择比任何启发式都准，且启发式会在学习通改版时静默失灵。

### 提醒

- **规则引擎抽为纯函数**：现有的候选收集逻辑重构为无 I/O 的纯计算 —— 输入待办集合、提醒历史、当前时间，输出「计划提醒」列表。每条计划提醒携带：待办 ID、规则 ID、触发时刻、打扰强度。两端共用同一套规则，Windows 消费「此刻该触发的」，Android 消费「未来该排的」。

- **两档规则**：截止前 24 小时（静默强度）、截止前 2 小时（响铃强度）。规则档位本轮硬编码，用户可配置留作 backlog。

- **去重键增加规则 ID**：现有去重键为「待办 ID + 类型 + 截止时间快照」，缺少规则维度，两档规则会互相吞掉。新键为「待办 ID + 类型 + 规则 ID + 截止时间快照」。这同时修正了产品文档术语表与代码实现之间既有的不一致（文档写的是含 `remindRule`，代码没有）。

- **新增 `ReminderScheduler` 抽象**：用于 Android 预排闹钟，提供排程与按 ID 取消。与现有的「立即弹通知」抽象并存而非合并 —— 二者语义不同（立即投递 vs 排到未来），合并会让两端实现都变脏。

- **闹钟排程范围与重排策略**：所有已知的、有截止时间的、未过期的待办全部排上两档闹钟，不设时间上限。每次同步后按 ID 全量取消并重排，使闹钟状态收敛到最近一次同步的真相。不设上限是因为 Android 每个应用 500 个并发闹钟的硬限制，按几十项待办 × 2 档计算用量不到四分之一；而设上限会造出新的静默失效（超出窗口的截止从未被排过闹钟，用户毫无感知）。

- **Android 投递模式**：两档都使用精确投递并允许在系统低电耗模式下触发。不使用非精确投递 —— 它在 Doze 期间可能把 2 小时档推迟到截止之后，那样这一档就完全失去意义。

- **Android 打扰强度**：通过两个通知渠道区分。24 小时档使用低重要性渠道（静默进通知栏），2 小时档使用高重要性渠道（响铃、震动、横幅浮出）。

- **Windows 强度不对称**：Windows 的通知机制只有一种强度，没有渠道重要性的概念。两档在 Windows 上表现完全相同。这是刻意接受的不对称，需写入领域术语表，否则会被误认为是缺陷。

- **新项目不触发即时提醒**：仅在到达规则时刻时提醒。

### 认证失效

- **失效事件化**：认证失效从「一条错误消息」升级为一个有状态的事件 —— 进入失效、通知一次、持续期间不再重复通知、重新登录成功后重置。

- **失效后停止自动同步**：认证失效后完全停止自动刷新（而非退避重试），直到用户重新登录。理由：失效的 Cookie 重试多少次都不会成功，继续请求只会增加被风控的风险。

- **两端呈现**：Windows 走系统通知 + 托盘图标与状态文字变化；Android 走应用内醒目横幅 + 一键跳转登录。

### Android 登录

- **登录界面泛化**：现有的 Windows 登录界面与其后端抽象提升为平台无关的登录界面，Windows 与 Android 各自提供后端实现。现有抽象的形状已经支持这一点，Android 后端是纯增量添加。

- **Cookie 形态不对称**：Android 侧取回的 Cookie 只有名称、值、域、路径，**没有 Secure 与 host-only 标记**，与 Windows 侧从 Cookie Store 取到的结构不同。它会落到 Cookie 存储模块中已有的扁平 Cookie 字符串兼容路径上。这一点必须显式处理并测试，不能假设两端同构。

- **权限**：清单中声明免用户授权的精确闹钟权限与开机广播接收权限，并声明插件提供的开机重排接收器。通知权限在首次登录成功后于运行时请求。选择免授权的精确闹钟权限而非需用户授权的那个，是因为后者在 Android 14+ 对新装应用默认拒绝；而前者的应用商店政策限制不适用于侧载分发。

### 分发与更新

- **新增 `AutostartService` 抽象**：包装开机自启注册，写入当前用户注册表运行键，启动参数包含隐藏启动标志。默认关闭，设置页提供开关。

- **隐藏启动分支**：现有的 Windows 启动流程无条件显示主窗口。需要分支：带隐藏启动标志时初始化托盘与定时器但不显示窗口。

- **安装包**：使用 Inno Setup 产出单文件安装程序，安装到当前用户的本地程序目录以避免 UAC 提权。同时继续发布 ZIP 便携版。不购买代码签名证书，接受首次运行的 SmartScreen 警告。安装程序检测 WebView2 运行时并在缺失时引导安装。

- **更新检查**：查询 GitHub Releases 接口比对构建号，仅提示并提供跳转到发布页的入口，不自动下载或安装。

- **URL 信任分级拆分**：现有的 URL 策略模块把「从学习通页面抓取来的 URL」和「编译期写死的常量 URL」混在同一套校验里。拆成两类：抓取来的 URL 属于不可信输入，必须过严格的学习通主机白名单；编译期常量 URL（如发布页地址）属于可信，以具名常量的形式单独提供。这是为了让更新检查能跳转到 GitHub 而不必削弱针对抓取 URL 的安全约束。

## Testing Decisions

### 什么是好的测试

**只测外部可观察行为，不测实现细节。** 具体到本 spec：

- 性能优化的断言对象是**发出了哪些 HTTP 请求**，不是内部有没有某个缓存字段、缓存命中率是多少。「同一轮同步里首页只被请求一次」是行为；「`_homeCache` 非空」是实现细节。
- 提醒的断言对象是**产出了哪些计划提醒**（待办 ID、规则 ID、触发时刻、强度），不是内部用了什么数据结构遍历。
- 一个好的测试在重构后应该继续通过。如果把课程扫描的内部循环改写一遍会让测试失败，那测试写错了。

### 主接缝：`LocalSyncRunner` + `MockClient`

**决策 6~16（全部同步性能与受监控课程相关的行为）在这一个已有接缝上测试，不新建接缝。** 该接缝注入 HTTP 客户端与时钟，能观测到每一个发出的请求。测试方式为记录请求 URL 序列并断言：

- 一轮同步中首页 URL 恰好出现一次
- 任务列表 URL 只包含受监控课程的标识，未监控的课程不产生请求
- 同一天第二次同步不出现课程发现相关 URL；推进注入的时钟跨天后出现
- 已知通知 ID 的详情 URL 不再出现
- 第一页命中已知通知 ID 后，后续页码的请求不存在
- 手动刷新课程列表后立即出现发现请求

**Prior art**：现有的同步链路测试已经用这个模式（注入 `MockClient` 返回构造的 HTML/JSON，断言产出的同步响应）。新测试沿用同一套写法，只是额外记录请求 URL。

### 提醒规则引擎：纯函数，无 fake

规则引擎重构为纯计算后，测试无需任何 fake、无需异步、无需平台：给定待办集合、提醒历史、当前时间，断言产出的计划提醒列表。覆盖：

- 24 小时档与 2 小时档各自在正确时刻产出
- 两档互不吞噬（验证去重键含规则 ID）
- 截止时间变化后重新产出
- 同一档在同一截止时间快照下只产出一次
- 无截止时间、已过期的事项不产出
- 强度标记正确（24 小时档静默、2 小时档响铃）

**这是本 spec 中最高价值的测试集合** —— 两端共用同一套规则，逻辑只需验证一次。

**Prior art**：现有的提醒服务测试已覆盖去重历史的裁剪与候选收集，重构后这些用例需要迁移到新的纯函数形态。

### `ReminderScheduler` fake

只断言**排了哪些、取消了哪些**，不断言底层插件如何被调用。重点用例：同步后全量重排时，旧闹钟被取消且新闹钟被排上；重排前后 ID 一致以保证取消能命中（社区反复报告过取消不干净导致残留闹钟持续报错的问题）。

**Prior art**：现有的托盘服务测试用 fake bridge 断言状态更新序列，同一模式。

### `AutostartService` 双层验证

- 单元测试：注入 fake，断言注册时传入的参数包含隐藏启动标志、默认状态为关闭、开关切换调用正确的方法。
- 端到端脚本：在真实 Release 产物上断言注册表运行键的实际值、静默安装与卸载的结果、带隐藏启动标志运行时不出现窗口但进程存在。

**Prior art**：已有的 Windows 单实例验证脚本就是这一层的先例，新增断言并入同一套脚本或其同级脚本，由 CI 执行。

### 控制器层

在已有的控制器接缝（注入存储、抓取器、认证器、时钟）上测试：缓存优先渲染、认证失效后自动同步停止、失效通知只发一次、重新登录后状态重置、渐进渲染过程中列表的中间状态。

**Prior art**：现有的控制器测试已覆盖缓存优先加载与限流退避恢复，同一写法。

### Android 平台行为

清单中的权限与接收器声明由 CI 静态检查（现有 CI 已检查禁止备份、禁止明文流量、禁止 HTTP VIEW，扩展即可）。Cookie 形态不对称走 Cookie 存储模块的既有测试，新增一组只带名称/值/域/路径的输入用例。真机上的响铃、震动、重启后闹钟存活、点击跳转属于手动验收，列入清单。

### 手动验收清单

自动化覆盖不到的：Windows 通知肉眼可见性、通知点击后窗口恢复并跳转详情、五项托盘菜单、退出后进程确实结束、首次运行的 SmartScreen 表现、Android 真机响铃与点击跳转、安装程序在无 WebView2 运行时机器上的引导行为。

## Out of Scope

- **任务详情分级缓存**：明确推迟。等上述优化实测之后再判断是否需要付出「数据可能陈旧数小时」的代价。
- **提高任何并发度**：已有实测证据表明会适得其反。
- **用户可配置的提醒档位**：本轮硬编码 24 小时与 2 小时，可配置留作 backlog。

- **Cloudflare Worker、CalDAV、Google Calendar、ICS 订阅、远端同步接口**：全部为历史架构，本轮从文档中删除相关说明，不做迁移。
- **绕过学习通验证码、二次验证或风控**。
- **iOS、macOS、Linux**。

## Further Notes

### 实施顺序

同步链路优化（决策 6~16）**两端共同受益**，因此排在 Windows 阶段而非 Android 阶段之后。完整顺序：

1. 提交当前工作树上已有的改动
2. 文档：领域术语表、产品文档瘦身、README 删除历史架构说明、一份架构决策记录
3. 同步链路优化 → 实测
4. Windows 闭环：两档提醒、失效可见性、自启、安装包、更新检查、自动化验证
5. 实际使用一周
6. Android：登录、闹钟、权限

第 5 步是刻意的 —— 只有真正用过一周，才知道 Windows 端还缺什么，也才知道任务详情缓存到底需不需要做。

### 只写一份架构决策记录

仅为「Android 采用预排本地闹钟而非后台抓取」立档，因为它同时满足难以回退、缺少背景会让人困惑、存在真实权衡三个条件。两档提醒、仅提示更新、安装程序选型均不立档 —— 它们容易更改、不令人意外，或没有真正的权衡。

### 预期效果

同步总耗时从 18.6 秒降至 12 秒上下，其中课程扫描阶段从 5.7 秒降至约 1.5 秒（发现阶段 3 个串行请求降为 0，课程列表请求从 20 门 × 2 降为约 7 门 × 2）。首屏感知延迟为 0。这些数字是估算，实施后需实测复核。

### 安全边界（沿用，不得削弱）

Cookie 只进安全存储，不进普通偏好、日志、诊断导出、通知正文或界面回填。所有带 Cookie 的请求走统一客户端并限制在显式学习通 HTTPS 主机白名单内，不接受任意子域，重定向手动校验且不得携带 Cookie 跟随到白名单外。外部浏览器跳转同样受限。错误摘要、失败列表与诊断导出脱敏 Cookie、token、账号类参数与响应正文。手动 Cookie 输入在源级拒绝换行注入（整份拒绝：不认证、不保存、不发送），保存成功后清空输入框。密钥库与本地环境变量文件不得提交或上传，CI 从干净检出构建且不注入真实凭据，发布产物上传前审计。
